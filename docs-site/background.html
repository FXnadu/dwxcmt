Background

为什么需要一套自建的、无冗余依赖、低内存占用、高性能、易部署的评论系统？

01

背景与痛点

个人博客、静态文档站（Hexo / Hugo / VitePress 等）普遍依赖 Twikoo、Waline 等第三方评论服务，这些方案存在以下四大痛点：

痛点影响
依赖外部服务第三方服务一旦关停、改版，评论功能即不可用，站点的读者互动能力完全受制于人。
资源开销大Node.js 运行时内存占用高，对于 1 核 1G 的小型服务器是沉重负担。
数据不自主评论数据存放在他人平台，迁移成本高，无法真正拥有自己的社区内容。
部署复杂依赖 Node.js 环境、云函数等，运维繁琐，升级与备份都需要额外学习成本。
结论 需要一套 无冗余依赖、低内存占用、高性能、易部署 的自建评论系统。
02

产品定位

极致轻量的自托管评论系统：单二进制 + 单文件数据库 + 纯静态前端

替代对象

Twikoo、Waline 等轻量评论服务

目标用户

技术博客作者、静态站点站长、自托管爱好者

核心理念

极致轻量、零重型依赖、数据完全自主、运维成本极低

03

设计目标（质量属性）

目标量化指标优先级
极致轻量后端单二进制 + 单数据库文件，前端打包 ≤ 25KBP0
低资源占用整机服务总内存 ≤ 100MB，适配 1 核 1G 服务器P0
高性能接口响应毫秒级，支持千级日活P0
高稳定无第三方平台依赖，常驻无冷启动，长期免人工干预P0
易部署运维编译即交付，复制文件即上线，支持一键备份升级P0
体验友好表情、回复提醒、数据迁移、图片等实用功能P1
04

适用场景与范围

类别内容
适用场景个人博客（Hexo / Hugo / VitePress 等静态站）
文档站点、个人作品站
日访问量 ≤ 5000、日均评论 ≤ 200 的中小站点
需要完全自托管、避免第三方服务关停风险的场景
明确不做（非目标）评论者注册 / 登录体系（零门槛）
用户编辑 / 删除自己的评论（发后不改）
富文本 / 完整 Markdown 编辑器（仅纯文本 + 图片 URL + Emoji）
实时推送 / WebSocket（采用轮询式刷新）
评论软删除、取消赞、举报功能
超出规模说明 上述「日访问量 ≤ 5000、日均评论 ≤ 200」是产品定位声明，而非容量上限：它用于划定「为谁设计」的边界，避免读者误判。实测读路径真实容量约 4.4 万 req/s（5 实例并行、限流放宽口径）、写路径真实吞吐约 1,000 条/s，实际余量远大于该数值。真正限制项目规模的，是以下设计取舍而非性能：
限制维度设计取舍影响
SQLite 单写者写入串行（单文件锁）评论由「人类打字」产生，天然低频，完全够用；机器批量灌流量时写入排队
全量审核 + 无用户体系所有评论人工审核、评论者零门槛日均 200 条一人可审；日均数千条时，审核人力成为运营瓶颈
功能边界无注册登录 / 实时推送 / 编辑删除高流量社区所需的产品形态不在本项目范围内，属刻意取舍

判断方法：访问量大但评论量中等 → 直接使用，读路径是强项；评论量真正巨大（日均数千条以上）→ 需要带用户体系与机器人防护的社区方案，超出本项目定位。

05

用户角色定义

角色定位核心诉求
访客浏览博客并发表评论的普通用户快速发表、表情 / 图片支持、回复通知、无需注册
被回复者收到回复通知的评论者通过邮件收到回复提醒
站长 / 管理员博客所有者全量审核、删除垃圾、置顶、数据备份迁移、第三方绑定
