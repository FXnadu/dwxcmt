## 2. 本地压测结果

### 2.1 读压测（列表查询，5 实例 × 20 并发 × 30s，20 个页面）

| 实例 | QPS | 平均延迟 | p99 | 响应数 | 状态码 |
|---|---|---|---|---|---|
| worker1 | 43,602 | 0.6 ms | 1.7 ms | 1,000,000 | 全部 200 |
| worker2 | 8,806 | 2.3 ms | 13.3 ms | 264,233 | 全部 200 |
| worker3 | 8,723 | 2.3 ms | — | 261,764 | 全部 200 |
| worker4 | 8,940 | 2.3 ms | — | 268,260 | 全部 200 |
| worker5 | 8,852 | 2.3 ms | — | 265,584 | 全部 200 |
| **合计** | **≈ 78,900** | **0.6~2.3 ms** | **<14 ms** | **2,059,841** | **0 错误** |

- 读路径合计吞吐约 **7.9 万 req/s**，平均延迟亚毫秒级~2ms，最长 173ms，零错误、零非 200。
- 说明：读压测阶段数据库为空（写压测在其后进行），走的是空列表快速路径；worker1 因最早启动独占 CPU 时段，QPS 明显高于后启动的 worker，属于调度现象而非性能差异。

### 2.2 写压测（提交评论，8 worker × 20s）

| 指标 | 数值 |
|---|---|
| 成功入库（code=0） | 999 条 |
| 全局限流（code=2001） | 1,768 |
| 每日上限（code=2002） | 347 |
| 重复拦截（code=2003） | 0 |
| 业务错误（code=1xxx） | 0 |
| HTTP 失败 / 5xx | 0 |

- **重要说明**：`stress.ps1` 中 `(, $ips)` 的 PowerShell 数组包裹写法导致 `$ipPool` 实际为单元素数组，XFF 头变成了整个 IP 池拼接串，**全部写请求被服务端归属为同一个 IP**（查库确认 `DISTINCT ip = 1`，rate_limits 计数恰好 1000）。因此写压测实际验证的是「单 IP 攻击者」最坏场景。
- 该场景下表现：每秒限流 50 rps 与每日 1000 条上限**精确生效**，成功写入数恰好触顶（999 ≈ 上限 1000），被拒请求全部以业务码 2001/2002 返回（HTTP 仍为 200，与设计一致），**无 4xx/5xx、无业务异常**。
- 修正 IP 随机化后补充的原始写吞吐测试（6 worker × 10s，各自独立 IP）：10 秒内成功写入 **1,577 条 ≈ 158 条/s，0 错误**。瓶颈在客户端 curl 逐进程开销，服务端写路径健康。

### 2.3 内存与 goroutine（泄漏判定）

| 指标 | 基线 | 压测峰值 | 压测后（GC 后） |
|---|---|---|---|
| WorkingSet | 15.8 MB | 43.7 MB | 28.3 MB |
| HeapInuse | 2.4 MB | 5.2 MB | 3.9 MB |
| goroutine | 11 | — | 11 |

- 峰值 WorkingSet 43.7MB，仅为 1G 机器建议阈值（600MB）的 7%；GC 后堆仅增长 ~1.5MB，对应压测期间新增约 2,600 条评论数据，合理。
- goroutine 全程稳定 11 个，无协程泄漏。
- 堆快照（pprof）top 均为 runtime 内部结构（`runtime.mallocgc` 75%、`net/http.readRequest` 缓冲、`runtime.newm` 线程栈），**无业务对象堆积，判定无内存泄漏**。

## 3. 线上部署效果（cmt.example.com）

### 3.1 可达性与延迟

- 健康检查 `GET /api/v1/health`：HTTP 200，版本 `0.1.0`。
- 连续 10 次延迟采样（含 DNS/TCP/TLS）：

| 分位 | TTFB |
|---|---|
| 首次（冷连接） | 140 ms |
| 稳定后中位数 | ≈ 58 ms |
| 稳定后范围 | 50~73 ms |

- 网络 RTT 约 22ms，服务端处理时间为毫秒级，TTFB 主要由网络链路决定；早期单次观测的 600ms 为冷启动/首包抖动，非持续状态。
- 主站 `example.com` 首页 total 1.7s（评论服务仅为其中嵌入组件，非本服务问题）。

### 3.2 功能与安全验证

| 检查项 | 结果 |
|---|---|
| 评论列表 API | 正常，返回真实数据（roots + children 树结构，含站长回复 isAdmin=1） |
| 站点配置 API | 正常 |
| CORS 白名单 | 允许的 Origin（`https://example.com`）正确返回 `Access-Control-Allow-Origin`；未白名单 Origin 无 CORS 头（浏览器将拦截） |
| CORS 预检 OPTIONS | 204 + 完整 Allow-Headers/Methods/Max-Age=86400 |
| **线上限流** | 12 连发同 IP → 6 成功 + 6 被限流（业务码 2001，HTTP 200），**5 req/s/IP 精确生效** |
| **IP 伪造防护** | 外部伪造 `X-Forwarded-For` 无效：Nginx 追加真实 IP、服务端从右向左取第一个非可信 IP（P0-2 修复验证通过） |
| TLS | 证书校验通过（ssl_verify_result=0） |
| 静态资源缓存 | `Cache-Control: max-age=604800, public, immutable` + ETag（7 天强缓存） |

### 3.3 线上小并发压测

hey 40 请求、并发 5：平均 14.3ms，HTTP 全部 200（业务码层面被限流拦截，HTTP 语义保持正常），未出现任何 5xx/连接错误。线上限流在毫秒级返回，不会拖垮服务。

## 4. 结论

1. **性能达标**：本地读路径 ~7.9 万 req/s、亚毫秒~2ms 延迟；写路径原始吞吐 ≥158 条/s（受客户端工具限制，非服务端瓶颈），单 IP 最坏场景下精确执行 50 rps + 1000 条/日配额，全程 0 错误、0 5xx。
2. **内存稳定**：峰值 WorkingSet 43.7MB（阈值 600MB 的 7%），GC 后堆无增长，goroutine 无泄漏，1G 内存机器可长期稳定运行。
3. **线上运行健康**：TTFB ~58ms（以网络 RTT 为主），限流、CORS、TLS、静态缓存、IP 伪造防护全部按设计生效，业务数据读写正常。

## 5. 建议

1. **修复压测脚本缺陷**：`scripts/stress.ps1` 写压测 IP 池 `(, $ips)` 数组包裹导致 IP 随机化失效（本次实测等效单 IP 场景）。如需多 IP 写压测，将 `-ArgumentList ..., (, $ips)` 改为 `-ArgumentList ..., $ips`（`stress.sh` 无此问题）。
2. **线上长稳观测**：若需确认 24h+ 内存表现，可在服务器执行 `bash scripts/monitor.sh $(pgrep -f light-comment) /var/log/lc-monitor.csv` 按小时采样后再汇总。
3. **本报告测试产物均已清理**：`stress.db`、临时查询脚本、压测用 `light-comment.exe` 已删除，本地服务已停止，不影响仓库与线上环境。
