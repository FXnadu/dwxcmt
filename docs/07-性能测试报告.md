## 0. 口径说明（重要，先读）

- 本报告所有数字均来自一次完整压测编排（`scripts/bench-all.ps1`），各阶段逐一给出原始文件与采样量，**可复现**。
- **读路径口径修正**：早期版本报告的「7.9 万 req/s」实为**限流响应被计入吞吐**——读接口也走全局限流，被 2001 拒绝的请求仍返回 HTTP 200，hey 按 HTTP 状态码统计时把这些拦截响应算成了成功 QPS。本次改用 `config-bench.yaml`（限流放宽至 100 万，等效不限流）测量真实容量，结果见 §2.1。
- 旧报告中 worker1 = 43,602 req/s 的异常值**未复现**：本次 5 个实例 QPS 在 8.7k~9.2k 的窄带内，无调度偏斜。
- **HTTP 错误 ≠ 业务码拒绝**：限流拒绝（2001/2002）是设计内行为，HTTP 状态仍为 200；本报告单独统计「HTTP 错误」（连接失败 / 5xx / 超时）与「业务错误」（code=1xxx）。

### 2.2 写路径 · 单 IP 最坏场景（`write-a.json` / `write-a-per-sec.csv`，25s）

配置：严格实例（50 req/s/IP + 1000 条/日/IP）；负载：32 并发线程，全部请求伪造同一 IP `203.0.113.50`（TEST-NET-3 保留段），攻击速率 ≈ 800 req/s，总请求 19,447。

| 业务码 | 数量 | 说明 |
|---|---|---|
| code=0（成功入库） | **1,000** | **精确触顶每日上限 1000 条** |
| code=2001（每秒限流拒绝） | 18,197 | 50 req/s 精确生效 |
| code=2002（每日配额拒绝） | 250 | 通过每秒限流但超出日配额 |
| code=2003（重复拦截） | 0 | — |
| code=1xxx（业务错误） | **0** | — |
| HTTP 错误（连接失败/5xx/超时） | **0** | — |
| 平均延迟（含被拒请求） | 0.67 ms | — |

- 理论校验：每秒限流 50 req/s × 25s = 1,250 个放行请求 = 1,000（成功）+ 250（日配额拒绝）✓；拒绝 19,447 − 1,250 = 18,197 ✓
- 逐秒数据（`write-a-per-sec.csv`）：前 20 秒 `code0 = 50/s`（每日未触顶，每秒精确放行 50 个成功）；第 20 秒起 `code0 = 0`、`code2002 = 50/s`（每日 1000 触顶后放行的请求全部被日配额拒绝）；`code2001 ≈ 710~740/s` 全程恒定；**http_error 逐秒全 0**。
- 图表：[03-write-strict-timeseries.png](../docs-site/images/perf/03-write-strict-timeseries.png)、[04-write-strict-codes.png](../docs-site/images/perf/04-write-strict-codes.png)
- 服务端日志 `strict-server.err.log` / `out.log` 均 0 字节（无 panic、无异常输出）。

## 4. 结论（基于本次实测数据）

1. **读路径真实容量 ≈ 44,481 req/s**（5 实例并行、空库列表查询、限流放宽等效不限流），单实例 8.7k~9.2k req/s、平均 2.2~2.3ms、p99 ≤ 11.8ms（<14ms）、1,334,644 次响应 0 错误。独立逐请求采样 p99 = 2.2ms、p99.9 = 8.2ms。
2. **写路径单 IP 最坏场景（800 req/s 攻击）**：每日上限 1,000 条与每秒限流 50 req/s **精确生效**（成功 1,000 触顶、2001 = 18,197、2002 = 250），**0 业务错误、0 HTTP 错误**；放宽限流下真实写吞吐 ≈ 1,008 条/s。
3. **内存**：单实例 WorkingSet 峰值 29.2MB、HeapInuse 峰值 7.7MB、goroutine 峰值 147（读压测），压测后回落，无泄漏。**1 核 512MB 机器可运行**（占用约 5%）。
4. **线上运行健康**：TTFB ~58ms（以网络 RTT 为主），限流、CORS、TLS、静态缓存、IP 伪造防护全部按设计生效。

## 5. 防失真措施（写给非技术读者）

把压测想象成"考试"。下面每一条都在回答同一个问题：**这个分数会不会是蒙对的、抄来的、或者老师放水给的？**

### 5.1 用专业工具监考，不靠人工数数
- **做了什么**：用 hey（业界标准压测工具）生成请求、用 Go 官方 pprof 采样内存，全部自动记录。
- **防止什么**：人工数错、掐表不准、"觉得大概有这么多"。
- **怎么证明**：每次测量都有原始文件（响应数、延迟逐条记录），不是回忆出来的数字。

### 5.2 两套考卷分开：一张考"规则"，一张考"能力"
- **做了什么**：限流验证用严格配置（每秒最多 50 条、每天最多 1000 条）；容量测量用放宽配置（等效不设限）。
- **防止什么**：把"被规则拦下的请求"误当成"成功的请求"。旧报告 7.9 万 req/s 的虚高就是这么来的——被限流的请求仍返回 HTTP 200，被误计为成功。
- **怎么证明**：严格配置下成功数精确停在 1,000 条；放宽配置下才测出真实容量 44,481 req/s。

### 5.3 大样本：不是考一次，是考 133 万次
- **做了什么**：读路径累计 133.4 万次请求、延迟单独采样 60.5 万次、写压测逐秒记录 25 秒。
- **防止什么**：碰巧发挥好或发挥差的一次让结果失真。
- **怎么证明**："60 万里 99% 在 2.2 毫秒内"比"100 次里 99% 在 2.2 毫秒内"可信得多。

### 5.4 先怀疑"监考老师"自己，再下结论
- **做了什么**：排查并修复了三处"压测客户端干扰"——
  1. 写压测客户端由每次新建连接改为持久连接，消除了 Windows 临时端口耗尽产生的 9,694 个"假 HTTP 错误"；
  2. 旧报告用 curl 测出写吞吐 158 条/s，怀疑是客户端慢，换专业客户端实测 1,008 条/s；
  3. 内存用 pprof 且不强制 GC，避免测到"被清理后的假内存"。
- **防止什么**：把压测工具自己的毛病记到服务端头上。
- **怎么证明**：三处修复后，"0 错误""1,008 条/s""29.2MB"才是服务端的真实表现。

### 5.5 异常值当警报处理，不平均掉
- **做了什么**：旧报告曾出现单实例 43,602 req/s 的异常值，本次重新测量后未复现，已从报告剔除。
- **防止什么**：一个异常高的值把平均数拉高，让人误以为更快。
- **怎么证明**：本次 5 个实例 QPS 都在 8.7k~9.2k 的窄带内，无偏斜。

### 5.6 服务端全程留底
- **做了什么**：压测全程服务端日志单独存文件。
- **防止什么**：嘴上说"没报错"，实际报错被刷掉看不见。
- **怎么证明**：两份服务端日志文件均 0 字节——全程没有任何 panic 或异常输出。

### 5.7 可复现：谁都能重考
- **做了什么**：一键脚本 `scripts/bench-all.ps1` 自动完成全部压测，原始 CSV 全部保留。
- **防止什么**：数字死无对证。
- **怎么证明**：按 §6 复现方式重跑，即可得到同规格的数据。

### 5.8 主动写清边界，不吹成"生产保证"
- **做了什么**：报告明确标注"本机压测、空库、限流放宽"三个前提，并给出生产折算建议（按 1/5~1/10 打折看）。
- **防止什么**：把"实验室上限"当成"生产承诺"。
- **怎么证明**：结论只承诺方向正确的部分（容量远超需求、512MB 够用、限流精确），不承诺绝对数值。

## 6. 复现方式与建议

1. **复现**：`go build -o %TEMP%\dwx-stress.exe main.go` 后以 `config/config-stress.yaml` 启动；再执行 `powershell -ExecutionPolicy Bypass -File scripts\bench-all.ps1`（自动切换 bench 实例并产出全部原始数据）；最后 `python scripts/gen-perf-charts.py <产物目录> --charts-dir <输出>` 渲染图表。
2. **关于旧报告数据**：`docs/07-性能测试报告.md` 早期版本的「7.9 万 req/s / 158 条/s / 43.7MB」分别受「限流响应计入 QPS」「curl 客户端瓶颈」「单次观测偏差」影响，已由本次实测修正；如需比对，原始产物已归档于 `%TEMP%\lc-bench-20260813-114952\`。
3. **线上长稳观测**：如需确认 24h+ 内存表现，执行 `bash scripts/monitor.sh $(pgrep -f dwx-comment) /var/log/lc-monitor.csv` 按小时采样后再汇总。
4. 本次压测产物目录（`%TEMP%\lc-bench-20260813-134650\`）保留全部原始 CSV/JSON 与图表；`stress.db`、`bench.db` 等压测数据库均位于独立路径，未影响仓库与线上环境。
